02 • PI EXPLAINED

What Is Pi?

Pi

Pi is the coding-agent harness we are using.

It is the environment around the LLM that lets an agent receive instructions, use tools and skills, work with files, and produce results.

User / TaskWhat needs to be done
→
Pi HarnessRuns the agent loop
→
LLMReasons and decides
↔
Tools / SkillsTake actions
↔
Files / DataProvide context
Important: Pi is not the AI model itself. In my setup, Qwen is the model. Pi is the harness that lets the model operate as an agent.
The easiest way to explain Pi is: Qwen is the brain, but Pi is the working environment around the brain. Pi lets the model receive a task and use tools, files, skills, and instructions to actually do work.
03 • WHY PI MATTERS

An Agent Needs More Than an LLM

Agent=Model+Tools+Instructions+Rules+Harness

Model

Reasoning and language.

Tools

Files, commands, APIs, search, databases.

Instructions

The job, goal, handoff, and expected output.

Rules

What the agent can and cannot do.

Harness

Pi runs the agent loop and connects these parts.

Verification

Checks that important results are correct.

This is why my Pi role matters. If we only focus on the model, we miss the tools, instructions, permissions, and verification that decide whether an agent is actually reliable.

12 • AGENT RULES

Rules I Think We Need Around Our Agents

Least Access

Give each agent only the tools, files, and services it actually needs.

Clear Objective

The agent should know its job, expected output, and when the task is complete.

Source Evidence

Important technical claims should point back to a source document or graph evidence.

Verification

The extractor should not be the only thing deciding whether its own result is correct.

Human Approval

Important requirement or design changes should wait for a person before being committed.

Audit Trail

Log important agent actions, tool calls, approvals, failures, and changes.

These rules connect directly to my security and monitor responsibilities. The goal is not to stop the agents from working. The goal is to make their work controlled, reviewable, and traceable.

15 • HOW WE TEST THE GRAPH

Questions Should Force the LLM to Navigate Relationships

01

Which components depend on the same voltage requirement as SENSOR_A?

02

If CONTROLLER_B changes logic voltage, what connected components or interfaces may be affected?

03

Which source document supports this requirement and the component connected to it?

04

Find components that use I2C and also depend on a 3.3 V logic level.

05

If an interface is removed, what becomes indirectly affected through the graph?

Goal: We do not only want keyword lookup. We want to prove the LLM can follow the graph and explain the path it used.
JR asked for clever questions. I think the best questions are ones where the answer requires multiple hops in the graph, not just finding one node by name.
